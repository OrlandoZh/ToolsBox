# 路线 4 本地存储决策

> 用途：记录“未来若进入路线 4（轻服务能力）时，本地缓存优先写哪里”的项目侧判断。
> 范围：这是决策记录，不是 current truth；它不打开新 wave，不改变默认 `release` / `gate` 语义。
> 更新时间：2026-04-16

## 结论先看

- 若未来路线 4 需要把小体量控制面数据落到本地，当前优先级应为：
  - `zotero.sqlite` 优先于 `prefs`
  - `zotero.sqlite` 优先于普通明文文件
- 这个优先级只成立在一个限定前提下：
  - 目标是降低普通开发者、自动化工具和一轮 AI 对本地缓存内容的直读门槛
- 它**不**意味着：
  - `zotero.sqlite` 构成新的安全边界
  - `sqlite + 本地解密` 足以承担真正的授权根或 secrets protection

## 为什么优先 `zotero.sqlite`

相对 `prefs` 与普通文件，`zotero.sqlite` 的优势主要是认知层和检索层的：

- `prefs` 很显眼：
  - key 名通常可读
  - 路径稳定
  - 很容易被导出、截图、搜索或直接交给 AI 解读
- 普通文件也很显眼：
  - JSON / txt / cache / js 这类文件容易被文件浏览和全文检索直接命中
  - 一旦路径和文件名带语义，AI 很快就能归纳用途
- `zotero.sqlite` 至少多了一步：
  - 需要先知道有表
  - 再知道表名/字段
  - 再串起 query / decode / use 路径

因此，如果只是想避免“别人一眼在 `prefs` 或文件里看到关键字段、策略文案、许可缓存”，把这类数据优先落到 `zotero.sqlite` 是合理的。

## 这条判断不能被高估的地方

`zotero.sqlite` 只是更隐蔽的本地缓存载体，不是新的信任边界。

只要插件本地代码里仍然存在以下任一项，分析者最终仍可顺着同一路径恢复数据：

- 建表或查询逻辑
- 表名和字段名
- 解密函数
- key 派生规则
- 数据被读回业务逻辑的入口

所以这条路线更准确的语义是：

- **提升直读成本**
- **延迟暴露**
- **降低首轮静态扫描命中率**

而不是：

- 真正保密
- 强授权保护
- 对抗有心分析者

## 本地存储决策矩阵

| 数据类型 | 优先存储 | 原因 | 不应怎么做 |
|------|------|------|------|
| 用户可编辑设置、开关、主题、调试项 | `prefs` | 这类数据本来就应可读、可排查、可恢复 | 不要为了“藏”而强塞进 DB |
| 小体量远端策略包、feature policy、provider catalog 快照 | `zotero.sqlite` | 比 `prefs` / 文件更不显眼，适合做结构化缓存、过期时间和版本管理 | 不要把它包装成强安全边界 |
| 短时授权态、ticket、订阅状态缓存 | `zotero.sqlite` | 适合做低频缓存、版本号、签名状态和过期信息落地 | 不要把最终授权根放在本地 |
| 长文本控制数据、希望降低直读暴露的服务端响应 | `zotero.sqlite` | 比明文文件更难被首轮检索直接命中 | 不要把完整业务主体下发并长期缓存 |
| 调试工件、可导入导出的配置包 | 普通文件 | 需要可见性、迁移性、人工排查便利 | 不要误当作保护手段 |
| 长期 secrets、许可根、主密钥 | 不应本地长期保存 | 这类信息应尽量留在服务端或缩短为临时状态 | 不要落到 `prefs`、文件或 `sqlite` 再声称安全 |

## 当前 retained rule

若未来路线 4 落地，本地存储应遵守以下规则：

1. `sqlite` 只承担小体量控制面缓存，不承担真正授权根。
2. 本地缓存默认是后置拉取后的结果，不绑定 `bootstrapPlugin` 的首次可用。
3. 远端失败时只降级，不因缓存缺失或表损坏阻断插件启动。
4. 本地优先做签名校验、过期时间和版本戳，不优先做“本地再 AES 一层”的伪强保护。
5. 表结构和字段命名应减少过于直白的业务语义，但不为了混淆而牺牲可维护性到不可控。
6. 若本地仍保存可推导密钥、固定 passphrase、明文解密函数与稳定查询路径，就不得把该方案描述成强保护。

## 对路线 4 的具体影响

这条决策意味着未来若进入 `ai-service` 或其他轻服务能力波次，优先考虑的是：

- 服务端签发：
  - 短时 token / ticket
  - feature policy
  - provider catalog
  - 许可 / 订阅状态
- 客户端本地只缓存：
  - 可过期状态
  - 小体量策略
  - 低频控制面

不优先考虑的是：

- 客户端本地激活码作为主授权判断
- 把整套业务主体下发到本地后再解密执行
- 把 `sqlite + 本地解密` 宣称为核心防盗版手段

## 何时需要重开判断

只有出现以下情况之一，才需要重新评估这条决策：

- 当前威胁模型从“阻碍普通开发者与一轮 AI 快速直读”升级为更强对抗目标
- 计划把远端策略绑进启动主链
- 计划在本地长期保存更高价值的许可根或密钥材料
- 准备引入 Wasm 小内核或更明确的服务端授权闭环
